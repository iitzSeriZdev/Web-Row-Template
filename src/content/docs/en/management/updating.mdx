```bash
row-template update
```

This downloads the **latest stable release**, verifies it, and applies it. Your branding and your chosen design are kept.

<Callout type="info" title="The command always applies the latest release">
  `row-template update` does not compare versions: it re-applies the latest release even when you already run it, which makes it a dependable repair. The manager's **1 — Update** is the one that checks first and asks — see [The interactive manager](/docs/management/manager/#manager-or-commands).
</Callout>

## What happens

<Steps>

### Download and verify

The release is fetched from GitHub (or from `RT_RELEASE_DIR` / `RT_RELEASE_URL`), its SHA-256 checked, and the archive screened and extracted — exactly as in a fresh install.

### Check the new release

The new page is validated, every installer file the release declares must be present and match its checksum, and all of the release's designs are verified into the template store. Any problem stops the update here, **before anything is changed**.

### Keep your design

Your current design is taken from the new release's copy. If the new release no longer includes it, Row is used and you are warned.

### Back up

A snapshot of the current installation is taken. If it cannot be, the update stops.

### Stage and activate

The new page, `VERSION`, the management library, its components and the `row-template` command are installed, then the live page is regenerated from the new version with your branding, validated, and swapped in.

</Steps>

A successful update prints:

```text
  Updating Row-Template 1.1.0 -> 1.2.0
  ok   Update complete: now running 1.2.0.
```

followed by the live checks. Old backups are then pruned to the two newest.

## If activation fails

The previous version is restored from the snapshot automatically:

```text
  FAIL activation of the new version failed; rolling back.
  warn rolled back to 1.1.0; no changes are live.
```

The command exits with status `1`. Your subscribers keep seeing the previous page throughout. If the automatic restore also fails — which needs two independent failures — you are told to run `row-template rollback`.

## Upgrading from 1.1.0

Updating from 1.1.0 takes **two runs** of `row-template update`:

<Steps>

### First run — done by 1.1.0's updater

```bash
row-template update
```

The command you run is still 1.1.0's. It installs 1.2.0: the page updates and your branding is kept. But 1.1.0's updater only copies the library and the command, so the template store and the new installer components are not installed yet, and only Row is available.

### Check

```bash
row-template verify
```

It tells you the second run is needed:

```text
  FAIL template store missing or empty; run 'row-template update' to install it.
  warn installer components are missing (lib/transaction.sh, panels/), as after an update from 1.1.0; run 'row-template update' to complete the installation.
```

### Second run — done by 1.2.0

```bash
row-template update
```

Now the 1.2.0 updater runs. It installs every design and the remaining installer files. `row-template verify` then passes, and you can [choose a design](/docs/templates/choosing/).

</Steps>

In the manager, **1 — Update** recognises this state and offers `Re-install 1.2.0 now to complete it?`.

## Updating without GitHub access

Point the update at a folder containing a release you downloaded and verified yourself:

```bash
RT_RELEASE_DIR=/root/row-template-X.Y.Z-release row-template update
```

See [Manual installation](/docs/installation/manual/#updating-an-offline-server).

## What an update never changes

- Your **branding** (`config.env`).
- Your **design**, while the new release ships it.
- Your **panel settings** — `subThemeDir` already points at the install directory, which does not move.
- Your existing **backups**, apart from pruning to the two newest valid ones.

To go back to the version you had before an update, use [rollback](/docs/management/rollback/).
